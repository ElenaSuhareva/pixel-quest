# PIXEL QUEST — общая инструкция для ИИ-разработчика

> Этот файл — главный технический и дизайн-бриф проекта.  
> Его нужно использовать как источник истины при создании сайта и всех игровых страниц.
>
> Проект: учебный игровой сайт с витриной из 3 мини-игр, общей системой профиля ученика и общим балансом алмазов.

---

# 1. Главная идея проекта

Создать небольшой образовательный игровой сайт **PIXEL QUEST** в стиле яркой 2D pixel-art RPG.

На сайте есть:

- приветственный экран при первом входе;
- главная страница-витрина с 3 играми;
- отдельная страница каждой игры;
- сама игра;
- профиль ученика;
- единый баланс алмазов для всех игр;
- учебные задания, встроенные внутрь игрового процесса;
- сохранение имени, баланса и прогресса локально в браузере.

Это **не сайт с тестами, оформленными как игра**.

Главный принцип:

> Сначала ученик играет.  
> В определённый момент игровое действие вызывает короткое учебное задание.  
> После ответа ученик сразу возвращается в игру.

Учебное задание должно ощущаться как часть приключения, а не как переход в отдельный школьный тренажёр.

---

# 2. Цель для ученика

У ученика должно быть ощущение собственного игрового профиля и общего прогресса.

Во всех играх используется одна общая валюта:

## Алмазы

Алмазы начисляются за правильные ответы на учебные задания.

Пример базовой логики:

- правильный ответ: `+10 алмазов`;
- неправильный ответ: `-3 алмаза`;
- баланс не должен становиться отрицательным;
- после ошибки обязательно показать правильный ответ;
- после показа ответа игра продолжается;
- одна ошибка не должна заставлять начинать игру сначала.

Количество начисляемых и снимаемых алмазов должно храниться в настройках, а не быть разбросано по коду.

Например:

```ts
const REWARD_CORRECT = 10;
const PENALTY_WRONG = 3;
```

---

# 3. Главное правило проекта

Нельзя превращать каждое действие в упражнение.

Нужен ритм:

```text
игра
→ игровое действие
→ короткое задание
→ результат
→ награда / штраф
→ сразу обратно в игру
```

Игровая часть должна занимать заметно больше времени, чем окно задания.

Задания должны появляться после логичных игровых событий:

- дошёл до контрольной точки;
- открыл сундук;
- выбрал грядку;
- нашёл кристалл;
- победил простого противника;
- открыл дверь;
- активировал рычаг;
- собрал предмет;
- достиг нового участка карты.

---

# 4. Пользовательский сценарий

## Первый вход

Если ученик открывает сайт впервые:

1. Показать приветственный экран на весь экран.
2. Попросить ввести имя.
3. Кнопка: **«Начать приключения»**.
4. После нажатия:
   - сохранить имя локально;
   - создать профиль;
   - установить баланс алмазов `0`;
   - перейти на главную страницу.

Если имя уже сохранено, приветственный экран повторно не показывать.

Текст:

```text

Как тебя зовут?
```

Поле:

```text
Имя ученика
```

Кнопка:

```text

```

# 8. Витрина из трёх игр

Каждая карточка должна быть похожа на маленькую игровую сцену.

Карточка содержит:

1. большое pixel-art превью;
2. небольшую тематическую иконку;
3. название;
4. короткое описание;
5. кнопку **«Играть»**.

Карточки не должны выглядеть как обычные карточки SaaS-сайта.

Использовать:

- толстую светло-бежевую pixel-art рамку;
- тёплый кремовый фон нижней части;
- тёмный пиксельный текст;
- зелёную объёмную кнопку;
- золотые акценты;
- лёгкую пиксельную тень.

# 9. Три игры

Рабочая структура первой версии:

## Игра 1. Храбрый рыцарь

Короткое описание:

> Отправляйся к замку, проходи препятствия и выполняй задания.

Пример механики:

- герой движется по дороге к замку;
- путь разбит на несколько небольших участков;
- игрок кликает по следующей точке или управляет героем;
- в некоторых контрольных точках появляется задание;
- правильный ответ даёт алмазы;
- затем открывается следующий участок пути.

---

## Игра 2. Фермерская долина

Короткое описание:

> Выполняй задания, поливай грядки и выращивай волшебный сад.

Базовая механика:

- на поле 10 пустых квадратных грядок;
- рядом фермер с лейкой;
- ученик кликает по грядке;
- открывается учебное задание;
- после ответа фермер подходит или проигрывается короткая анимация полива;
- на грядке вырастает растение / цветок;
- правильный ответ даёт бонусные алмазы;
- при ошибке показывается правильный ответ, снимается небольшой штраф и игра продолжается;
- цель: заполнить все 10 грядок.

---

## Игра 3. Пещерные приключения

Короткое описание:

> Исследуй пещеру, собирай сокровища и открывай новые участки.

Пример механики:

- простая 2D пещера;
- герой перемещается по небольшим платформам;
- собирает монеты / кристаллы;
- открывает сундуки;
- некоторые сундуки или двери вызывают задания;
- правильные ответы дают алмазы и открывают проход дальше;
- цель: добраться до сокровища в конце уровня.

# 12. Учебные задания

Все игры должны использовать единый универсальный компонент задания.

Например:

```text
QuestionModal
```

Он не должен быть отдельно написан заново для каждой игры.

## Структура задания

```ts
type Question = {
  id: string;
  type: "choice" | "input";
  prompt: string;
  options?: string[];
  correctAnswer: string;
  explanation?: string;
};
```

Пример:

```ts
{
  id: "prefix-1",
  type: "choice",
  prompt: "Выбери правильный вариант: пр...ехать",
  options: ["и", "е"],
  correctAnswer: "и",
  explanation: "ПРИ- пишется в значении приближения."
}
```

---

# 13. Поведение окна задания

Когда наступает игровой триггер:

1. игровой процесс временно останавливается;
2. появляется крупное модальное окно в pixel-art стиле;
3. ученик выбирает или вводит ответ;
4. нажимает «Ответить»;
5. система проверяет ответ.

### Правильный ответ

Показать:

```text
Верно!
+10 💎
```

Можно добавить:

- короткую анимацию кристалла;
- лёгкое свечение;
- короткий игровой звук.

После небольшой паузы:

```text
Продолжить
```

или автоматический возврат в игру через 1–1,5 секунды.

### Неправильный ответ

Показать:

```text
Пока неверно.

Правильный ответ:
ПРИЕХАТЬ

-3 💎
```

Если есть объяснение:

```text
ПРИ- обозначает приближение.
```

Затем:

```text
Продолжить
```

Ошибка **не заканчивает игру**.

# 16. Работа с localStorage

Создать отдельный слой, например:

```text

```

Функции:

```ts

createPlayer(name)
updatePlayerName(name)
getDiamonds()
addDiamonds(amount)
removeDiamonds(amount)
```

# 23. Общая игровая логика заданий

У игр должен быть единый интерфейс взаимодействия с системой вопросов.

Игра сообщает:

```text
triggerQuestion(questionId)
```

Система задания:

1. получает нужный вопрос;
2. показывает `QuestionModal`;
3. проверяет ответ;
4. обновляет общий баланс;
5. возвращает игре результат.

Например:

```ts
type QuestionResult = {
  correct: boolean;
  diamondsDelta: number;
};
```

Игра затем решает, что делать дальше:

```ts
onQuestionComplete(result)
```

Важно:

> Образовательная логика и игровая механика должны быть разделены.

Так потом можно будет менять задания, не переписывая игру.

# 24. Система вопросов должна быть заменяемой

Сегодня тема может быть:

- приставки ПРИ-/ПРЕ-;

завтра:

- спряжение;
- НЕ с разными частями речи;
- Н и НН;
- суффиксы;
- орфограммы корня.

Поэтому игра не должна знать, что именно изучается.

Игра знает только:

```text
«в этой точке нужно показать вопрос»
```

А вопрос приходит из данных.

# 25. Дизайн-система

Основной стиль проекта:

## 2D pixel art fantasy

Референсы:

- приветственный экран — вложение №1;
- главная страница — вложение №2;
- логотип — вложение №3.

Ключевые признаки:

- крупная читаемая пиксельная графика;
- яркий fantasy-мир;
- синие и фиолетовые интерфейсные панели;
- золотые рамки;
- кремовые карточки;
- зелёные игровые кнопки;
- голубое небо;
- зелёные острова / платформы;
- замки;
- кристаллы;
- мягкие пиксельные тени;
- тёплая игровая атмосфера.

# 27. Шрифты

## Основной интерфейсный шрифт

Для кириллицы использовать пиксельный шрифт с хорошей читаемостью.

Предпочтительно:

```text
Pixelify Sans
```

Он подходит для:

- заголовков;
- кнопок;
- карточек;
- подписей;
- русскоязычного UI.

Пример через `next/font` или локальную настройку Google Font.

Важно:

- не вставлять `@import` Google Fonts посреди CSS-файла;
- если используется CSS `@import`, он должен находиться в самом начале файла;
- лучше использовать `next/font/google`, если проект на Next.js.

Пример:

```ts
import { Pixelify_Sans } from "next/font/google";

const pixelFont = Pixelify_Sans({
  subsets: ["latin", "cyrillic"],
  weight: ["400", "500", "600", "700"]
});
```

Если конкретная версия Next.js не поддерживает нужный subset или шрифт, проверить документацию и выбрать ближайший пиксельный кириллический шрифт.

---

# 28. Логотип

Логотип из референса №3 должен использоваться как отдельный графический asset.

Не пытаться собирать весь логотип обычным HTML-текстом.

Он включает:

- пиксельный щит;
- меч;
- надпись `PIXEL QUEST`;
- белый `PIXEL`;
- золотой `QUEST`;
- подзаголовок:

```text
ИГРАЙ. ИССЛЕДУЙ. МЕЧТАЙ.
```

Для сайта подготовить:

```text
logo-full.png
logo-full.webp
logo-compact.png
logo-mark.png
```

`logo-mark` — только щит/меч для маленьких размеров.

---

# 29. Pixel-perfect UI

Все основные элементы должны быть стилизованы.

Нельзя оставлять стандартными:

- `<button>`;
- `<input>`;
- карточки;
- модальные окна;
- progress bar.

Создать повторно используемые компоненты:

```text
PixelButton
PixelPanel
PixelFrame
PixelInput
PixelModal
DiamondBadge
```

---

# 30. Кнопки

Основная кнопка:

- ярко-зелёная;
- золотая внешняя рамка;
- тёмная нижняя грань;
- небольшой эффект объёма;
- пиксельная тень;
- белый текст;
- hover — чуть светлее;
- active — визуально нажимается вниз.

Не использовать современную размытую `box-shadow`, характерную для SaaS.

Тень должна быть жёсткой или почти жёсткой.

---

# 31. Pixel-art рамки

Не делать рамку просто так:

```css
border: 2px solid orange;
```

Нужен эффект игровой рамки:

- несколько внутренних линий;
- светлая верхняя грань;
- тёмная нижняя грань;
- угловые декоративные элементы;
- небольшая пиксельная тень.

Для важных панелей допускается использовать готовый PNG/WebP nine-slice asset.

---

# 32. Изображения и качество

Все игровые иллюстрации должны быть подготовлены отдельно.

Не пытаться нарисовать сложный замок, героя, мага, дракона и пещеру CSS-ом.

CSS используется для:

- позиционирования;
- кнопок;
- рамок;
- панелей;
- простых эффектов.

Графика используется для:

- персонажей;
- ландшафтов;
- замков;
- кристаллов;
- логотипа;
- иллюстраций карточек.

---

# 33. Форматы ассетов

Использовать:

- `PNG` — когда нужна прозрачность и максимально предсказуемое качество;
- `WebP` — для больших фоновых изображений;
- `SVG` — только для простых интерфейсных иконок, если они не должны выглядеть пиксельными.

Для pixel-art не применять размытие.

CSS:

```css
.pixelArt {
  image-rendering: pixelated;
}
```

Применять осознанно: только к настоящим pixel-art ассетам.

---

# 34. Масштабирование pixel-art

Идеально, если исходные игровые ассеты создаются в небольшом базовом разрешении, а затем увеличиваются кратно:

```text
1x
2x
3x
4x
```

Избегать дробного масштабирования, которое делает пиксели нечёткими.

---

# 35. Анимации

Допустимы короткие анимации:

- подпрыгивание алмаза;
- мерцание кристалла;
- лёгкое движение героя;
- полив растения;
- появление цветка;
- открытие сундука;
- мигание звезды;
- нажатие кнопки.

Не превращать экран в постоянную анимацию.

Главная задача — сохранить читаемость.

---

# 36. Звуки

Звук необязателен в первой версии.

Если добавляется:

- короткий звук правильного ответа;
- мягкий звук ошибки;
- получение алмаза;
- нажатие кнопки;
- открытие сундука.

Обязательно:

- возможность выключить звук;
- не запускать громкую музыку автоматически.

---

# 37. Адаптивность

Основной приоритет:

```text
desktop / ноутбук / интерактивная доска
```

Но интерфейс должен корректно уменьшаться на планшете.

Минимальная ширина игрового содержимого должна быть продумана.

На маленьком экране:

- карточки переходят из 3 колонок в 1;
- шапка упрощается;
- декоративные элементы могут скрываться;
- игровое поле сохраняет понятную композицию.

Не допускать горизонтального скролла всей страницы.

---

# 38. Доступность

Несмотря на игровой стиль:

- кнопки должны быть настоящими кнопками;
- интерактивные элементы доступны с клавиатуры;
- input связан с label;
- текст имеет достаточный контраст;
- вопрос можно ответить без мыши;
- нельзя передавать смысл только цветом.

Например, при ошибке писать:

```text
Неверно
```

а не просто красить карточку в красный.

---

# 39. Состояния загрузки

Изображения не должны дёргать layout после загрузки.

Для крупных изображений задавать размеры / aspect-ratio.

Не показывать пустые белые зоны.

Допустимо использовать pixel-art skeleton / фон нужного цвета.

---

# 40. Ошибки, которых нужно избежать

Запрещено делать:

1. обычный белый сайт с тремя прямоугольными карточками;
2. интерфейс в стиле современного SaaS;
3. полупрозрачный glassmorphism;
4. случайные emoji вместо игровых ассетов;
5. десятки разных шрифтов;
6. слишком мелкий пиксельный текст;
7. генерацию сложных персонажей чистым CSS;
8. отдельный баланс в каждой игре;
9. потерю прогресса при переходе между страницами;
10. перезагрузку всей страницы после каждого ответа;
11. превращение каждого шага игры в задание;
12. завершение игры после одной ошибки;
13. отрицательный баланс алмазов;
14. хранение логики начислений внутри каждой игры;
15. копирование одного и того же `QuestionModal` три раза;
16. создание backend для первой версии без необходимости.

---

# 41. Критерии готовности общей оболочки

Оболочка сайта считается готовой, когда:

- при первом входе появляется приветственный экран;
- имя сохраняется;
- после перезагрузки имя остаётся;
- на главной отображается имя;
- на главной отображается общий баланс;
- есть три игровые карточки;
- карточки ведут на три отдельные страницы;
- на каждой странице есть кнопка «Играть»;
- кнопка запускает игровой экран;
- общий компонент задания умеет показывать вопрос;
- правильный ответ меняет баланс;
- неправильный ответ показывает правильный ответ и меняет баланс;
- баланс сохраняется после перезагрузки;
- данные общие для всех трёх игр;
- визуально сайт соответствует приложенным pixel-art референсам.

# 42. Порядок разработки

Не создавать сразу все три игры.

Работать по этапам.

## Этап 1. Ассеты и дизайн-система

Сначала:

- подготовить логотип;
- фон главной;
- фон приветственного экрана;
- мага;
- героя;
- дракона;
- карточные иллюстрации;
- рамки;
- кнопку;
- алмаз;
- декоративные элементы.

После этого создать UI-kit.

---

## Этап 2. Общая оболочка

Сделать:

- layout;
- header;
- welcome screen;
- localStorage profile;
- diamond counter;
- главную витрину;
- маршруты;
- страницы трёх игр.

Пока сами игры могут быть заглушками.

---

## Этап 3. Система заданий

Создать:

- структуру вопросов;
- QuestionModal;
- проверку ответа;
- правильный/неправильный feedback;
- начисление и списание алмазов;
- сохранение баланса.

Проверить эту систему отдельно.

---

## Этап 4. Сделать только первую игру

Полностью реализовать **Храброго рыцаря**.

На ней проверить:

- игровой цикл;
- появление заданий;
- баланс;
- сохранение прогресса;
- возврат в игру;
- визуальный стиль.

---

## Этап 5. После утверждения первой игры

Только после того, как первая игра визуально и технически принята:

- делать ферму;
- затем пещеру.

Не писать три игры одновременно.

# 43. Что делать с приложенными картинками

Сейчас три изображения являются **референсами**, а не готовой структурой сайта.

Следующий правильный шаг — превратить визуал в отдельные reusable assets.

## Из референса приветственного экрана нужны:

- фон без центральной панели;
- центральная светлая панель;
- рамка панели;
- логотип;
- герой;
- замок / окружение при необходимости;
- зелёная кнопка;
- маленькая иконка play;
- кристаллы;
- декоративные углы.

---

## Из референса главной страницы нужны:

- общий фон / environment;
- замок;
- дерево;
- водопад;
- горы / облака;
- дракон;
- волшебник;
- лента с приветствием;
- центральный золотой герб;
- карточная рамка;
- зелёная кнопка;
- иллюстрация рыцаря;
- иллюстрация фермы;
- иллюстрация пещеры;
- маленькие иконки;
- алмаз.

---

## Из референса логотипа:

подготовить отдельно:

```text
logo-full
logo-mark
shield
sword
```

Если логотип уже удачный, лучше использовать его как изображение, а не пытаться воспроизвести шрифтом.

---

# 44. Важное правило по работе с референсами

ИИ-разработчику нельзя самостоятельно «переосмысливать» референс и заменять его на произвольный дизайн.

Если предоставлены конкретные ассеты:

> Использовать их.

Если ассет ещё не подготовлен:

> Использовать временную заглушку с теми же пропорциями, но не придумывать новый визуальный стиль.

Композиция, размеры, рамки, цветовая логика и общая атмосфера должны повторять приложенные референсы максимально близко.

Перед крупной переделкой обязательно сделать commit рабочей версии.

# 47. Инструкция ИИ при написании кода

Перед каждым изменением:

1. сначала изучить существующую структуру проекта;
2. не удалять работающие части без необходимости;
3. объяснить, какие файлы будут изменены;
4. использовать уже существующие компоненты;
5. не дублировать логику;
6. не менять дизайн без запроса;
7. после изменений запустить build / typecheck;
8. исправить все ошибки;
9. только потом считать задачу выполненной.

---

# 48. Definition of Done для любой задачи

Задача считается выполненной только если:

```text
✓ код запускается
✓ нет build error
✓ нет TypeScript error
✓ маршруты работают
✓ изображения загружаются
✓ UI не разваливается
✓ localStorage работает
✓ после reload данные остаются
✓ внешний вид соответствует референсу
✓ не сломана предыдущая функциональность
```

Фраза «код готов» недопустима, если сборка не проверена.

---

# 49. Что пока НЕ делать

На первом этапе не нужны:

- регистрация;
- пароль;
- аккаунты родителей;
- серверная база;
- синхронизация между устройствами;
- магазин;
- реальные платежи;
- рейтинг всех учеников;
- мультиплеер;
- сложный RPG-инвентарь;
- 20 игр;
- сложная система уровней персонажа.

Сначала сделать маленькую, красивую и устойчивую игровую платформу.

# 50. Итоговая формула продукта

```text
PIXEL QUEST
=
единый профиль ученика
+
общий баланс алмазов
+
красивая pixel-art витрина
+
3 маленькие игры
+
короткие задания внутри игрового процесса
+
награда за правильные ответы
+
локальное сохранение прогресса
```

Главное ощущение для ученика:

> «Я не решаю тест. Я прохожу приключение, а задания помогают мне двигаться дальше».

Главное правило для разработчика:

> Сначала качественно собрать общую систему и одну игру.  
> Только после этого масштабировать её на остальные игры.
